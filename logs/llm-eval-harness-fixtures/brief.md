Google（日本）の上位10記事は見ていない。このセッションで使えた検索は WebSearch（米国向けの検索）だけで、2026-11-02 に「LLM 回答 自動採点 完全一致 部分一致 正規表現 評価 TypeScript」で検索した。返ったのは7件で、評価ツールの説明ページ（Braintrust の autoevals の TypeScript API、Mastra の Answer Similarity Scorer、LangWatch の LLM Answer Match）と、用語集（「完全一致 (Exact Match)」）だった。日本語の検索の上位とは別物なので、検索意図の判定の根拠にはしていない。

その7件から読み取れたこと（参考。記事の出典にはしていない）: 既製のツールは完全一致の採点関数を持ち、文体の違いは LLM に判定させる方向に寄せている。用語集は、完全一致が全角半角と句読点の違いで正解を取りこぼすことに触れていた。この記事は、既製のツールを使わずに数十行で同じ判定を書き、取りこぼしを NFKC の正規化で減らす。表記の揺れでは済まない判断は、講座の次の記事（LLM-as-a-Judge）に回す。

## 書き手の態度（guides/03 不在1）

採点が厳しすぎて不合格になった回答を見て、採点を緩めない。形の指定に合わない回答は受け取る側のコードで扱えないので、プロンプトの側で直す。もう1つは、部分一致は手軽なぶん間違った回答を合格にするので、数字のキーワードには使わない。この2つを記事の主張にした（`run/02.log` の不合格2件、`run/03.log` で部分一致が「13件」を合格にした結果）。

## 読み終えた人ができるようになること

自分のアプリのテストケースを、期待する答えの形に合わせて完全一致、部分一致、正規表現のどれかで採点する指定に書き、合格率と終了コードで合否を出すプログラムを動かせる。
